# EKF位置測定・GNSS誘導ロボット データ収集システム 設計要件書

- プロジェクト名: EKF位置測定GNSS誘導
- 作成日: 2026-09-19
- 対象: 本書はClaude Codeへの実装依頼用のインプットとして作成する

## 1. 目的・背景

本プロジェクトはEKF(拡張カルマンフィルタ)によりロボットの位置を推定し、定められた座標へ向かう誘導システムを構築するものである。本書はそのうち「走行中のセンサー・推定データを無線で漏れなく収集し、サーバー上のデータベースに保存する」データ収集サブシステムの設計要件を定める。

データ収集システムに求める性質は以下の2点である。

1. 走行中にリアルタイムで位置・姿勢・センサー値を監視できること
2. 走行後にログをまとめて解析できること(データの欠損を極力ゼロに近づけること)

## 2. システム全体構成

```
[ESP32-S3ファームウェア]
   ├─ エンコーダ(PCNT)      : 割り込み処理は行うが、実際の回転数への変換と取得はは10hz
   ├─ I2C: IMU(6軸)+気圧センサ : 10Hz
   ├─ UART: GNSSモジュール     : 1Hz
   └─ EKF位置推定             : 10Hz周期
        │
        │ Wi-Fi / MQTT (QoS1、切断時はローカルバッファリング)
        ▼
[Mosquitto (MQTTブローカー)]
        │
        ▼
[Telegraf] ── MQTT subscribe → InfluxDB書き込み(設定ファイルのみ、コード不要)
        │
        ▼
[InfluxDB (時系列データベース)]
        │
        ▼
[Grafana (リアルタイムダッシュボード / 事後解析)]
```

上記4コンポーネント(Mosquitto, Telegraf, InfluxDB, Grafana)はDocker Composeで一括構築する。運用はロボットが接続するWi-Fiルーターと同一ネットワーク内で完結させ、インターネット接続には依存しない。開発は手元のPC(Docker Desktop導入済み)で行う。

## 3. ハードウェア構成

- マイコン: ESP32-S3(デュアルコアXtensa LX7、最大240MHz、シングル精度FPU内蔵、Wi-Fi内蔵)
- エンコーダ: モーター回転数計測用(想定71rpm程度)
- 6軸センサ(IMU): I2C接続、加速度+角速度
- 気圧センサ: I2C接続、高度推定の補助
- GNSSモジュール: UART接続、1Hz測位
- 通信: Wi-Fiルーターの電波範囲内での運用を前提とする(長距離無線は対象外)

## 4. ファームウェア要件(ESP32-S3側)

###
### 4.1 無線送信要件(MQTT)

- プロトコル: MQTT、QoS1(少なくとも1回配信)を使用する
- 接続先: 同一Wi-Fiネットワーク上のMosquittoブローカー
- 送信周期: 10Hz(EKF推定値を含む統合レコードとして送信)
- 通信断対策: Wi-Fi/MQTT接続が切れている間は、内蔵フラッシュ(LittleFS)またはSDカードにリングバッファとして一時保存し、再接続後にまとめて再送する
- 各メッセージに連番(sequence number)と、GNSS由来のUTCタイムスタンプを付与し、サーバー側で欠落検出・重複排除・時刻順の並べ替えを可能にする
- ネットワーク切断・再接続、バッファ満杯時の挙動(古いデータから破棄する等)を明確に実装すること

### 4.2 送信データフォーマット(例、JSON)

```json
{
  "seq": 12345,
  "ts_utc": "2026-09-19T03:15:22.100Z",
  "pos": { "lat": 35.123456, "lon": 139.123456, "alt": 12.3 },
  "imu": { "ax": 0.01, "ay": -0.02, "az": 9.79, "gx": 0.1, "gy": 0.0, "gz": -0.1 },
  "baro": { "pressure_hpa": 1013.2, "alt_m": 12.1 },
  "encoder": { "right revloutions": 34.55676, "left revolutions": 42.44553 },
  "gnss": { "fix": 1, "hdop": 1.1, "sats": 9 },
  "EKF": { "position_N": 24.55, "position_E": 10.34, "speed": 0.75, "azimuth": 156, "bias_accel": 0.858685, "bias_gyro": 0.0374 }
}
```

フィールド構成は今後の詳細設計・実装時に調整可能とする。まずはJSON形式で開始し、通信量が問題になった場合にCBOR/MessagePack等のバイナリ形式への変更を検討する。

## 5. サーバー側要件

### 5.1 実行環境

- Docker / Docker Composeで構築する
- 開発はPC(Docker Desktop)上で実施する
- ロボットと同一Wi-Fiネットワーク内での運用とし、インターネット接続には依存しない

### 5.2 構成コンポーネント

| コンポーネント | 役割 |
|---|---|
| Mosquitto | MQTTブローカー。ESP32からのpublishを受信する |
| Telegraf | MQTTトピックをsubscribeし、InfluxDBへ書き込む(設定ファイルベースで実装、カスタムコード不要とする) |
| InfluxDB | 時系列データベース。全センサー値・EKF推定結果を保存する |
| Grafana | リアルタイムダッシュボードおよび走行後の解析用クエリインターフェース |

### 5.3 データ保持・管理

- 生データをInfluxDBに保存する
- リテンションポリシー・ダウンサンプリング方針は将来的に検討する(初期は無制限保持で可)
- 走行ログをCSV等でエクスポートし、Python等での事後解析が行えるようにする

### 5.4 可視化要件

- Grafanaで以下をリアルタイム表示できること: 現在位置(地図上、Geomapパネル等)、GNSS測位品質(fix状態・HDOP・衛星数)、EKF状態変数、センサ値
- 走行後の解析用に、任意期間のデータをGrafanaまたは直接InfluxDBクエリで取得できること

## 6. 非機能要件

- データ欠損防止: MQTT QoS1とオンボードバッファリングにより、通信断時もデータが失われず、後から補完されること
- リアルタイム性: サーバーがデータを受信してからダッシュボードに反映されるまでの遅延は数秒以内を目安とする
- 拡張性: 将来的なセンサー追加やEKF状態ベクトルの拡張に対応できるデータスキーマとする

## 7. スコープ外

- 目標座標へのナビゲーション制御ロジック(モーター制御・経路計画・誘導アルゴリズム)
- Wi-Fi範囲外での長距離無線通信(LoRa、セルラー通信等)
- EKFアルゴリズムそのものの詳細な数式設計・パラメータチューニング
